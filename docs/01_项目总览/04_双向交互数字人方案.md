# 04 双向交互数字人方案

> 评委建议：从单向手语识别升级为双向交互——加入"数字人输出手语"能力。  
> 撰写日期：2026-05-31  
> 目的：评估可行性，明确需要哪些技术、底层原理是什么、现有项目能复用多少、还缺什么。

---

## 一、目标定义

### 当前系统（单向识别）

```
听人说话 → 语音转文字 → （听人直接读文字）
聋人打手语 → 摄像头采集 → RTMPose 133关键点 → ST-GCN + mT5 → 文字输出 → 听人阅读
```

**问题**：聋人可以"发出"信息，但听人无法用手语"回复"聋人。沟通是单向的。

### 目标系统（双向交互）

```
┌─────────────────────────────────────────────────────────────────┐
│                      双向手语交互系统                              │
├─────────────────────────────────────────────────────────────────┤
│                                                                 │
│  听人 → 语音/文字 ──────────────────→ 文字显示（听人阅读）         │
│                  ┌────────────────→ 数字人手语播报（聋人观看）     │
│                  │                                              │
│  聋人 → 手语视频 → 133KP提取 → ST-GCN+mT5 → 文字显示（听人阅读）   │
│                                                                 │
└─────────────────────────────────────────────────────────────────┘
```

**新增链路**：`文字输入 → 手语生成 → 3D数字人动画 → 手语视频输出`

## 三、逐模块技术分析

### 模块 1：Text-to-Gloss（文本 → 手语词汇序列）

**底层原理**：
手语有自己的词汇和语法体系，与自然语言不是一一对应。例如中文"我今天很开心"对应的手语词汇序列可能是 `[我, 今天, 开心, 很]`（手语中程度副词常后置）。Text-to-Gloss 本质是一个**序列到序列的翻译任务**，将自然语言词序列映射为手语词汇序列。

**技术选型**：

| 方案 | 优点 | 缺点 |
|------|------|------|
| **mT5 微调** | 复用现有模型，训练成本低 | 依赖标注数据质量 |
| 专用 Transformer | 可定制词表和位置编码 | 需要从零训练 |
| LLM Prompt | 零样本能力强 | 推理速度慢，成本高 |

**现有项目可复用**：
- ✅ **mT5 模型和 Tokenizer**（`models.py:179-180`）— 已有加载和微调代码
- ✅ **CSL_Daily gloss 标注** — ~20K条文本-手语词汇对
- ✅ **CE_CSL gloss 标注** — ~87K条文本-手语词汇对
- ✅ **训练框架**（`fine_tuning.py`）— 可直接改造

**需要新增**：
- 逆向数据管线（text 作为输入，gloss 作为输出标签）
- Text-to-Gloss 专用评估指标（Gloss Accuracy, BLEU on gloss）

**可行性**：⭐⭐⭐⭐⭐ 高。mT5 + 现成标注数据，典型的 seq2seq 微调任务。

---

### 模块 2：Gloss-to-Pose（手语词汇序列 → 133关键点序列）

**底层原理**：

这是整个双向交互系统**最核心、最难**的模块。需要解决三个子问题：

**(a) 时长建模**：每个手语词汇持续多少帧？
- 不同词汇时长不同（"我"可能10帧，"中华人民共和国"可能80帧）
- 同一个词汇在不同语境下时长也不同
- 需要学习词汇→时长的映射（通常用 duration predictor）

**(b) 姿态生成**：每个词汇对应的关键点运动轨迹是什么？
- 输出是 133 个关键点的 (x, y, confidence) 序列，与项目现有的关键点格式完全一致
- 生成的质量要求：关节点轨迹平滑、骨骼长度恒定、手型准确、面部表情自然

**(c) 过渡生成**：词汇之间的过渡动作怎么生成？
- 两个词汇之间的"运动插值"不是线性插值那么简单
- 需要符合人体运动学约束（如手不会穿过身体）

**技术选型对比**：

| 方案 | 代表工作 | 原理 | 优点 | 缺点 |
|------|---------|------|------|------|
| **Autoregressive Transformer** | PoseGPT, MotionGPT | 逐帧自回归生成 | 序列建模强 | 误差累积，推理慢 |
| **Diffusion Model** | MDM, MotionDiffuse | 从噪声逐步去噪 | 生成质量最高 | 推理步数多 |
| **VQ-VAE + Transformer** | T2M-GPT, MoMask | 离散化+自回归 | 推理快，多样性好 | 训练复杂 |
| **Flow Matching** | MoFlow | 连续归一化流 | 最新SOTA | 实现复杂 |

**推荐方案：VQ-VAE + Transformer（MoMask 架构）**

```
训练阶段：
  133关键点序列 → VQ-VAE Encoder → 离散运动Token → VQ-VAE Decoder → 重建关键点
                                         ↑
                                  手语词汇序列（条件输入）

推理阶段：
  手语词汇序列 → Transformer → 离散运动Token → VQ-VAE Decoder → 133关键点序列
```

**为什么选这个方案**：
1. VQ-VAE 将连续运动压缩为离散 token，一个 token 代表约 0.2 秒的运动片段
2. Transformer 在离散 token 上做自回归生成，比在连续空间直接生成更稳定
3. 词汇序列作为 cross-attention 的条件输入，控制生成内容
4. 推理速度比扩散模型快 10-50 倍

**现有项目可复用**：
- ✅ **133关键点数据格式**（`datasets.py:18-75`）— 输出格式已定义
- ✅ **关键点归一化方案**（`datasets.py:80-105`）— [-1, 1] 坐标空间已定义
- ✅ **部位分组方案**（`stgcn_layers/gcn_utils.py:42-99`）— 身体9/左手21/右手21/面部18
- ✅ **训练数据** — CSL_Daily + CE_CSL 的 (视频→133KP→gloss) 三元组可直接用作训练

**需要新增**：
- VQ-VAE 运动编解码器（约 2000 行）
- Duration Predictor（词汇→时长）
- 条件 Transformer 生成器
- 运动质量评估指标（FGD, Diversity, MPJPE, 骨骼长度一致性）

**可行性**：⭐⭐⭐ 中高。姿态数据充足，但生成模型需要大量的调试和超参搜索。

### 模块 3：2D → 3D 关键点提升

**底层原理**：

当前项目的 133 关键点是 **2D 像素坐标 (x, y)**。要驱动 3D 数字人，需要 **3D 空间坐标 (x, y, z)**。

**技术方案**：

| 方案 | 原理 | 数据需求 | 精度 |
|------|------|---------|------|
| **直接 2D 映射** | 用固定深度层（z=0平面）渲染2D骨骼 | 无 | 低，但最简单 |
| **VideoPose3D** | 时序卷积从2D序列估计深度 | 2D标注+3D真值 | 中 |
| **SMPL-X Fitting** | 将2D关键点拟合到参数化3D人体模型 | 2D关键点 | 高 |
| **MotionBert** | Transformer 直接从2D序列回归3D | 2D+3D数据对 | 高 |

**推荐方案**：分两步走
- **MVP 阶段**：直接 2D 映射（2D 数字人也能传达手语信息，只是没有深度感）
- **完整版**：SMPL-X Fitting（学术界标准方案，有成熟开源实现）

**现有项目可复用**：
- ✅ 133 关键点已包含身体+手部+面部，覆盖 SMPL-X 所需的全部控制点
- ⚠️ 无 3D 标注数据，需要依赖预训练模型（如 SMPL-X 的 2D→3D regressor）

**需要新增**：
- SMPL-X 模型集成（`smplx` Python 包）
- 2D→3D 拟合管线（优化 SMPL-X 参数使投影误差最小）
- 或：VideoPose3D 预训练模型 + 微调

**可行性**：⭐⭐⭐⭐ 高（MVP用2D），⭐⭐⭐ 中（完整3D）。

### 模块 4：3D 数字人渲染

**底层原理**：

将 3D 骨骼动画数据驱动一个可视化的数字化身，实时渲染手语动作。核心组件：
1. **3D 模型**：带骨骼绑定（rigging）的人形模型
2. **动画系统**：根据关键点数据驱动骨骼旋转/位移
3. **渲染引擎**：实时渲染 3D 画面
4. **面部表情**：手语中面部表情是语法成分（疑问/否定/程度），不是可有可无

**技术选型**：

| 方案 | 技术栈 | 优点 | 缺点 |
|------|--------|------|------|
| **Three.js (Web)** | Three.js + GLTF模型 | 与现有React前端无缝集成 | 3D渲染性能受浏览器限制 |
| **Unity WebGL** | Unity + WebGL导出 | 渲染质量高，生态丰富 | 包体积大，加载慢 |
| **Blender离线渲染** | Python + Blender | 质量最高 | 不支持实时交互 |
| **Ready Player Me** | 云端API | 零开发成本 | 依赖第三方，定制性差 |

**推荐方案：Three.js + GLTF 模型（与现有 web 前端集成）**

```
前端架构（扩展现有 view/web/）：

┌──────────────────────────────────────────┐
│  React 19 + Vite + TypeScript            │
├──────────────────────────────────────────┤
│  现有组件              │  新增组件         │
│  · VideoPlayer        │  · AvatarCanvas  │
│  · PoseSkeletonViewer │  · SignAnimator  │
│  · LivePoseOverlay    │  · TextInput     │
│  · PredictionPanel    │  · TTS Engine    │
├──────────────────────────────────────────┤
│  现有 Hooks            │  新增 Hooks      │
│  · useLivePose        │  · useAvatar     │
│  · usePrediction      │  · useSignGen    │
│  · useSpeech          │  · useTTS        │
└──────────────────────────────────────────┘
```

**关键技术点**：

**(a) GLTF 骨骼模型**
- 需要一个带完整骨骼绑定的人形 GLTF 模型（免费的 Ready Player Me / Mixamo 模型）
- 骨骼层级：Hip → Spine → Shoulder → Arm → Hand (每个手指3段)
- 面部 blendshape（用于表情）

**(b) 关键点→骨骼旋转映射（IK/FK）**
```
133关键点 → 提取骨骼关节角度 → 驱动GLTF骨骼旋转

简化方案（前向运动学 FK）：
  关键点坐标差 → 关节旋转角 → 应用到骨骼

精确方案（逆向运动学 IK）：
  末端效应器位置（手腕/脚踝） → IK求解器 → 全部关节角度
```

**(c) 表情映射**
```
面部68关键点 → blendshape权重 → 驱动面部表情
简化方案：嘴部开合度 + 眉毛高度 + 眼睛开合度 → 几个关键blendshape
```

**现有项目可复用**：
- ✅ **React + TypeScript 前端框架**（`view/web/`）— 完整的现代化前端
- ✅ **FastAPI 后端**（`view/api_server.py`）— 可新增 `/sign/generate` 端点
- ✅ **WebSocket 或 SSE 支持** — 实现实时双向通信
- ✅ **133关键点数据结构** — 前端已有解析和渲染逻辑

**需要新增**：
- Three.js 依赖（`@react-three/fiber`, `@react-three/drei`）
- GLTF 人形模型文件（可免费获取）
- IK/FK 骨骼动画系统（约 500 行 TS）
- 表情 blendshape 映射表

**可行性**：⭐⭐⭐⭐ 高。Three.js 生态成熟，关键点驱动的骨骼动画有大量参考实现。

### 模块 5：语音 ↔ 文字（辅助模块）

**底层原理**：

完整的双向交互还需要语音能力，让听人能"说"给系统，系统"说"给听人。

```
听人 → 语音 → ASR(语音识别) → 文字 → Text-to-Gloss → ... → 数字人手语
聋人 → 手语 → 识别 → 文字 → TTS(语音合成) → 语音 → 听人
```

**技术选型**：

| 功能 | 浏览器端 (Web API) | 服务端 |
|------|-------------------|--------|
| ASR (语音→文字) | `webkitSpeechRecognition` | Whisper / 讯飞 |
| TTS (文字→语音) | `speechSynthesis` | Edge TTS / Azure TTS |

**现有项目可复用**：
- ✅ **Web Speech API** — 浏览器原生支持，已有 `use-speech.ts` hook
- ⚠️ 中文 ASR 在浏览器的 `webkitSpeechRecognition` 支持有限

**需要新增**：
- 服务端 ASR（推荐 Whisper，开源免费）
- 服务端 TTS 端点

**可行性**：⭐⭐⭐⭐⭐ 极高。浏览器原生 API + 开源模型。

## 六、分阶段实施路线图

### Phase 1：最小可行双向交互（4-6周）

```
文字输入 → Text-to-Gloss (mT5微调) → Gloss-to-Pose (简单检索+插值) → 2D骨架渲染 → 前端显示
```

- 不依赖复杂的生成模型
- Gloss-to-Pose 用最近邻检索（从训练集直接取对应词汇的关键点序列，拼接+平滑）
- 2D 骨架渲染用现有 `PoseSkeletonViewer` 组件
- 输出：用户打字 → 看到 2D 火柴人手语动画

**技术门槛**：⭐⭐ 低。大部分是工程拼接工作。

### Phase 2：学习式姿态生成（8-12周）

```
文字输入 → Text-to-Gloss → Gloss-to-Pose (VQ-VAE + Transformer) → 133KP序列 → 3D数字人 → Three.js渲染
```

- 训练 VQ-VAE 运动编解码器
- 训练条件 Transformer 生成器
- 集成 SMPL-X 做 2D→3D
- Three.js 3D 数字人渲染

**技术门槛**：⭐⭐⭐⭐ 高。需要深度学习研究经验。

### Phase 3：完整双向交互（12-16周）

```
听人 → 语音(ASR) → 文字 → Text-to-Gloss → Gloss-to-Pose → 3D数字人 → 手语视频
聋人 → 手语 → 摄像头 → RTMPose → ST-GCN+mT5 → 文字 → TTS → 语音
```

- 集成 ASR / TTS
- WebSocket 实时双向通信
- 用户体验打磨（延迟优化、UI 动画、无障碍适配）

**技术门槛**：⭐⭐⭐ 中高。系统工程。

## 七、关键技术风险与缓解

| 风险 | 严重程度 | 缓解方案 |
|------|---------|---------|
| **Gloss-to-Pose 生成质量不够** | 高 | Phase 1 用检索方案保底；Phase 2 迭代优化 |
| **手语词汇→动作不是唯一映射** | 中 | 生成时加入风格噪声，支持同一词汇的多种表达 |
| **3D 渲染性能不足（手机端）** | 中 | 提供 2D 骨架降级方案；LOD 优化 |
| **CSL_Daily gloss 质量参差不齐** | 中 | 数据清洗 + 人工抽检 + 数据增强 |
| **训练数据规模不够（~100K 条）** | 中 | 数据增强（时间扭曲、镜像、噪声注入） |
| **数字人面部表情不自然** | 低 | 手语中表情主要用于语法标记，可简化到 3-5 个关键表情 |

## 八、结论

### 回答三个核心问题

**Q1：这个可以实现吗？**

✅ **可以**。技术上没有不可逾越的障碍。核心模块（Text-to-Gloss、Gloss-to-Pose、3D Avatar）都有成熟的研究基础和开源实现可参考。

**Q2：目前项目已有的内容可以实现吗？**

⚠️ **部分可以**。现有项目提供了：
- 识别方向的完整链路（可继续使用）
- 133关键点数据格式和大量训练数据（可直接用于生成模型训练）
- mT5 模型和 gloss 标注（可用于 Text-to-Gloss）
- React + FastAPI 前后端框架（可扩展集成 3D 渲染）

**不能直接实现的**：Gloss-to-Pose 生成模型（核心挑战）、3D 数字人渲染（需新增）。

**Q3：还需要哪些东西？**

核心技术缺口：
1. **Gloss-to-Pose 生成模型**（从零构建，难度最高）
2. **3D Avatar 渲染引擎**（集成 Three.js，难度中等）
3. **2D→3D 关键点提升**（集成 SMPL-X，难度中低）
4. **ASR/TTS 语音模块**（集成现成方案，难度低）
5. **双向通信基础设施**（WebSocket，难度低）

### 一句话总结

> **从单向识别到双向交互，核心挑战不是工程量而是生成质量——关键点序列的生成需要在"准确表达手语语义"和"动作自然流畅"之间找到平衡。现有项目在数据、模型、前端三个方面都提供了坚实的基础，最需要从零攻坚的是 Gloss-to-Pose 生成模块。**
