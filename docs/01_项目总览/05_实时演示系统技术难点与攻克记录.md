# 05 实时演示系统技术难点与攻克记录

> 本文档面向互联网+比赛答辩，记录从研究原型到实时演示系统落地的关键技术难点和解决方案。

---

## 1. 概述

在完成 `CE-CSL` 离线训练和评估主线后，项目需要将研究模型转化为可实时交互的演示系统。这个过程中遇到了 7 个核心技术难点，均已攻克。

---

## 2. 技术难点清单

### 难点一：2.2GB 大模型实时推理延迟过高

**问题描述**

最佳模型 `round6` 完整版达到 2.2GB，包含 1012 个参数键（EfficientNet-B0 RGB 分支 + Pose GCN 分支 + mT5 文本解码器）。在 CPU 上单次推理需要 2-5 秒，完全无法满足实时演示需求。

**解决方案**

1. **模型分层部署**：实时推理使用 `stage3` pose-only 模型（1.1GB, 627 键，纯姿态分支），展示页使用 `round6` 完整模型（独立缓存，按需加载）
2. **GPU 推理加速**：模型通过 `model.cuda()` 移至 NVIDIA GPU，使用 `torch.inference_mode()` + BF16 精度
3. **贪心解码替代 Beam Search**：`num_beams: 6 → 1`，解码速度提升约 4 倍
4. **最大 token 数缩减**：`max_new_tokens: 100 → 50`，实时翻译通常不超过 25 个中文字符

**效果**

| 指标 | 优化前 | 优化后 |
|------|--------|--------|
| 模型加载 | 2.2GB, 90s | 1.1GB, 45s |
| 单次推理 | 2-5s (CPU) | 0.3-0.8s (GPU) |
| 解码方式 | Beam-6 | Greedy |

**关键技术点**

```python
# GPU 加速推理核心
model = model.cuda()
with torch.inference_mode():
    stack_out = model(src_input, tgt_input)
    output = model.generate(stack_out, max_new_tokens=50, num_beams=1)
```

### 难点二：姿态提取 CPU 瓶颈导致画面卡顿

**问题描述**

`RTMLib Wholebody` 133 关键点姿态提取在 CPU 上需要 80-120ms/帧，导致实时画面严重卡顿，无法跟随手部动作。

**解决方案**

1. **安装 `onnxruntime-gpu`** 替代 `onnxruntime`（CPU 版）

   ```bash
   pip install onnxruntime-gpu
   ```

   安装后 ONNX Runtime 自动启用 `TensorrtExecutionProvider` + `CUDAExecutionProvider`。

2. **输入分辨率缩减**：摄像头帧从 1920×1080 缩至 480p 宽度，ONNX 推理速度提升 3-4 倍

3. **独立姿态线程**：姿态提取在 daemon 线程中运行（8ms 轮询），完全解耦 WebSocket 事件循环

   ```python
   # 独立姿态线程 — 零阻塞
   def _pose_thread_worker():
       while True:
           frame = _latest_frame
           if frame is not None:
               kp, sc = process_pose_frame(frame)
               with _pose_lock:
                   _latest_pose = (kp, sc, ...)
           time.sleep(0.008)
   
   threading.Thread(target=_pose_thread_worker, daemon=True).start()
   ```

4. **异步发送器**：独立 asyncio 任务以 20fps 读取线程结果并推送前端

**效果**

| 指标 | 优化前 | 优化后 |
|------|--------|--------|
| 单帧姿态提取 | 80-120ms (CPU) | 5-15ms (GPU) |
| 端到端延迟 | 300-500ms | 50-100ms |
| 可用帧率 | ~8fps | ~20fps |

### 难点三：多人场景下姿态检测混乱

**问题描述**

RTMLib PoseTracker 在多人场景下会同时检测多人，导致骨架在多人之间跳动，模型无法正确识别目标人物的手语。

**解决方案**

在 `process_pose_frame()` 中实现**最大面积选择策略**：

```python
if n_persons > 1:
    best_area = -1
    for p in range(n_persons):
        valid = keypoints[p][scores[p] > 0.3]
        if len(valid) < 5: continue
        x_min, y_min = valid.min(axis=0)
        x_max, y_max = valid.max(axis=0)
        area = (x_max - x_min) * (y_max - y_min)
        if area > best_area:
            best_area = area
            best_idx = p
    keypoints = keypoints[best_idx]
```

**效果**

- 多人场景下自动锁定画面占比最大的人
- 过滤无效检测（<5 个高置信度关键点视为噪声）
- 单人场景零额外开销

### 难点四：WebSocket 实时通信链路延迟

**问题描述**

原始架构中，姿态提取 `await` 阻塞了 WebSocket 事件循环。每帧需要等待 100ms+ 的姿态提取完成后才能接收下一帧，形成"串行瓶颈"。

**解决方案**

采用**生产者-消费者架构**彻底解耦：

```
前端 (8fps)              后端
  │                       ┌─ 姿态线程 (8ms轮询, GPU)
  ├─ JPEG ──────────────►│    ↓ ONNX CUDA提取  
  │                       │    ↓ 存入 _latest_pose
  │                       ├─ 发送器 (20fps)
  │◄── pose_frame ────────┤    读取 → JSON → WebSocket
  │                       └─ 识别触发器
  ├─ 渲染骨架             
  │  (requestAnimationFrame)
```

**关键代码**

```python
# 帧接收 — 只存最新帧，不阻塞
elif "bytes" in data:
    frame = cv2.imdecode(...)
    frame_rgb = cv2.resize(frame, (480, ...))
    _latest_frame = frame_rgb  # 非阻塞更新

# 异步发送器 — 定时读取姿态线程结果
async def _pose_sender():
    while True:
        await asyncio.sleep(0.05)
        with _pose_lock:
            data = _latest_pose
        if data:
            await websocket.send_json(...)
```

### 难点五：前端骨架可视化性能优化

**问题描述**

COCO-133 关键点（身体 23 + 面部 68 + 左手 21 + 右手 21）的实时渲染涉及 65 条骨骼连线 + 133 个关节点。初始实现使用大尺寸关节点（半径 4.5px）和强发光效果（8px blur），在 1920×1080 画布上渲染时 GPU 占用高。

**解决方案**

1. **关节点微型化**：从 `r = 2.5-4.5px` 降至 `r = 0.3 + conf × 1.0`（与 eval 可视化一致）
2. **去除 CSS drop-shadow**：移除 8px blur 的全局画布阴影
3. **简化渲染管线**：去掉暗色轮廓层、白心高光、关键关节大发光
4. **颜色分区**：身体暖金 `#f0c060`、左手橙红 `#f09060`、右手翠绿 `#60d0a0`、面部淡紫 `#c0a0e0`
5. **requestAnimationFrame** 同步渲染与显示器刷新率

**效果**

- 渲染帧率稳定在 60fps
- 骨架线清晰流畅，信息密度提升
- 风格与 ModelShowcase 姿态提取可视化完全一致

### 难点六：前端录制倒计时与识别状态管理

**问题描述**

实时手语识别需要明确的"开始录制 → 结束录制 → 显示结果"流程。用户需要清晰的视觉反馈（倒计时、录制状态、结果展示）。

**解决方案**

1. **三阶段倒计时**：点击录制按钮 → `3 → 2 → 1 → 🎯` 全屏数字动画（0.8s/步，CSS `@keyframes countPulse`）
2. **录制中状态**：红色脉冲圆点 + 42px 计时器 + "正在录制手语..." 提示
3. **自动停止**：6 秒倒计时自动触发识别，也可手动点击停止
4. **进度环**：底部按钮周围 SVG 圆环，绿→橙→红渐变
5. **结果展示**：居中大字 + 置信度进度条 + 复制/朗读/删除操作

**前端关键逻辑**

### 难点七：多页面系统架构与资源管理

**问题描述**

项目包含 7 个功能模块（实时演示、模型展示、模型归因、智能学习、技术架构、应用场景、用户中心），需要管理两种模型（实时推理 + 展示推理），避免 GPU 显存溢出和多进程冲突。

**解决方案**

1. **单进程架构**：仅运行一个 FastAPI + Uvicorn 进程，WebSocket 和 REST API 共享同一个事件循环
2. **模型懒加载 + 独立缓存**：
   - 实时演示模型：`stage3`（1.1GB, pose-only）在启动时加载
   - 展示模型：`round6`（2.2GB, 完整版）通过 `_showcase_model_cache` 独立缓存，仅在访问展示页时加载
3. **归因数据源回退**：`eval CSV → 推理缓存 → 内存结果 → results.txt` 四级回退，确保数据始终可用
4. **SQLite 本地存储**：识别历史、用户认证、纠错记忆统一管理
5. **归档管理**：旧 Streamlit 系统移至 `view/archive/`，保持目录整洁

**系统架构**

```
view/
├── web_app/          ★ FastAPI 主应用
│   ├── app.py            后端全部逻辑 (单文件 2900+ 行)
│   └── vue-dist/         Vue.js 构建产物
├── web-frontend/     Vue.js 前端源码
├── archive/          已归档的旧 Streamlit 系统
└── 启动说明.txt      一键启动指南
```
